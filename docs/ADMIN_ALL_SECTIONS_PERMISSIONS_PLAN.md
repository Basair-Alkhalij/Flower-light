# توسيع صلاحيات الأدمن — خطة الأمان قبل التفعيل

**الحالة: معاينة واجهة فقط؛ تفعيل الصلاحيات الجديدة يحتاج موافقة صريحة على SQL.**

## النطاق المطلوب

يختار المدير بشكل مستقل ON/OFF لكل قسم من الأقسام الـ12 الموجودة في لوحة الإدارة:

- المنتجات والكتالوج: `sections` (الأقسام)، `products` (المنتجات)، `datasheet` (تصميم داتا شيت).
- المتابعة والتواصل: `leads` (العملاء)، `contacts` (وسائل التواصل)، `profile` (البيانات الشخصية)، `analytics` (الإحصائيات).
- الفلاتر والقوالب: `search-filters` (فلاتر البحث)، `template-settings` (قالب المنتجات).
- الموقع والمنشأة: `site-settings` (إعدادات الموقع)، `business-settings` (بيانات الشركة)، `bank-settings` (الحسابات البنكية).

`credentials` و`permissions` يبقيان للمالك فقط **دائمًا**. لا يُنشأ أدمن جديد، ولا تُمنح أي صلاحية افتراضية إضافية. الصلاحيات الحالية فقط هي `analytics`, `datasheet`, `profile`, `contacts`, `leads`.

## لماذا لا يصح تفعيل الأزرار فقط؟

- قيد `admin_users_permissions_check` ودالة `owner_set_admin2_settings` يرفضان مفاتيح الصلاحيات الجديدة.
- وظيفة Supabase `manage-admin-account` ترشح أي مفتاح غير مصرح به من الطلب.
- `admin.js` و`admin-navigation.js` ووحدات الإعدادات فيها قيود Owner-only مستقلة عن القائمة.
- `products` و`sections` لديهما سياسات RLS موجودة بالفعل، لكنهما غير قابلين للتفويض بسبب قيد الصلاحيات؛ أعمالهما تشمل الحذف ويجب اختبارها بعناية.
- جداول `site_settings` و`business_privacy_settings` و`business_public_fields` و`business_bank_accounts` تقيّد الكتابة للمالك. لا يجوز منح جميع الإعدادات لغير المالك مقابل السماح بإعداد واحد.
- مفاتيح `site-settings` و`template-settings` و`search-filters` تكتب إلى **صف مشترك** في `site_settings`. منح كتابة هذا الصف برخصة واحدة سيتيح تغيير إعدادات أقسام أخرى عبر API. الحل المستهدف: **دوال RPC منفصلة تتحقق من الدور والصلاحية وتسمح بالأعمدة المحددة فقط** بدل إطلاق UPDATE شامل.

## قبل دمج الميزة

1. موافقة مالك الموقع **بشكل مستقل** على مراجعة SQL وتطبيقه في مشروع Supabase الفعلي؛ هذه الخطوة ليست موافقة ضمنية.
2. تطوير SQL مرحلي قابل للتراجع، دون حذف البيانات أو منح `credentials` أو `permissions`.
3. اختبار أن الأدمن لا يستطيع تعديل أي جدول أو RPC أو ملف Storage خارج الأجزاء المُفعّلة له، بما في ذلك الطلبات اليدوية المباشرة.
4. تأكيد أن الحساب الحالي يحتفظ بصلاحياته نفسها وأن جميع المفاتيح الجديدة تكون OFF عند الانتقال.
5. تحديث قيود الواجهة والتنقل، وحدات الإعدادات، والـEdge Function، وعدم نشر الواجهة قبل انتهاء اختبارات الأمان.
6. اختبار الدخول والصلاحيات بمعرّفات مُحاكاة أولًا، ثم تطبيق SQL بعد النسخة الاحتياطية وبموافقة المالك.

**هذه الوثيقة والفرع المرتبط لا تنفذان SQL ولا تغيران `admin_users` أو بيانات Supabase.**

## ملف SQL الرسمي للمراجعة (لم يتم تشغيله)

- [فتح SQL المقترح](../supabase/PROPOSED_ADMIN_12_PERMISSIONS_REVIEW_ONLY.sql).
- الخطوة المقترحة لا تمنح الأدمن أي صلاحية جديدة تلقائيًا؛ تقتصر على إضافة مفاتيح التفويض والسياسات المقيدة والدوال المخصصة.
- **مهم:** لا يكفي SQL منفردًا لإكمال الميزة. يلزم بعده تحديث `admin.js` و`admin-navigation.js` ووحدات الفلاتر والموقع والقالب والشركة والبنوك، وكذلك `manage-admin-account` في Supabase Edge Functions، مع اختبارات عزل حقيقية لحساب الأدمن.
- خاصية الحسابات البنكية تحتاج إذن `bank-settings` فقط؛ إعدادات الشركة `business-settings` فقط. لا تُمنح كتابة كاملة لجدول `site_settings` لأحد غير المالك.
- توجد دوال منفصلة: `admin_set_site_toggle` و`admin_save_catalog_filters` و`admin_set_template_field` لتعديل أعمدة محددة. يظل حساب المالك وحده صاحب صلاحية منح الصلاحيات وتغيير بيانات الدخول.
- **تحذير الترحيل:** إعادة تنفيذ الملف الجامع القديم `SUPABASE_SETUP.sql` بعد الترقية قد تعيد القائمة القديمة للخمسة، لأنه يحتوي على مرحلة تقوية سابقة. عند الموافقة لاحقًا يجب تحديث المصدر الجامع أو ضمان تشغيل الترقية الجديدة بعده. لا تستخدم الآن أياً منهما على القاعدة الحية.

### مسار التفعيل اللاحق (بعد موافقة منفصلة)

1. تثبيت نسخة الرجوع وفحص النسخة الاحتياطية الموجودة، دون إعادة نسخ أو تعديل بيانات.
2. مراجعة SQL مع اختبار فشل الوصول غير المصرح في قاعدة اختبار معزولة، وليس إنتاج.
3. الموافقة الصريحة على تشغيل هذا SQL في المشروع الحقيقي بعد عرض النسخة النهائية حرفيًا.
4. اختبار صلاحيات الأقسام الـ12 بصلاحيات OFF أولًا، ثم اختبار كل مفتاح وحده وعدم تسرّب الصلاحيات الأخرى.
5. نشر تحديثات الواجهة ووظيفة إدارة الحسابات المتوافقة، وتفعيل أزرار الأقسام الجديدة فقط عندما تنجح الاختبارات.
6. تجربة عملية في حساب الأدمن مع عدم حذف أي منتج أو تعديل بيانات حقيقية أثناء التحقق.
