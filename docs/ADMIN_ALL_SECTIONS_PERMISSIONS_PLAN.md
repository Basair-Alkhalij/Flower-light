# توسيع صلاحيات الأدمن — خطة الأمان قبل التفعيل

**الحالة: معاينة واجهة فقط؛ تفعيل الصلاحيات الجديدة يحتاج موافقة صريحة على SQL.**

## النطاق المطلوب

يختار المدير بشكل مستقل ON/OFF لكل قسم من الأقسام الـ12 الموجودة في لوحة الإدارة:

- المنتجات والكتالوج: `sections` (الأقسام)، `products` (المنتجات)، `datasheet` (تصميم داتا شيت).
- المتابعة والتواصل: `leads` (العملاء)، `contacts` (وسائل التواصل)، `profile` (البيانات الشخصية)، `analytics` (الإحصائيات).
- الفلاتر والقوالب: `search-filters` (فلاتر البحث)، `template-settings` (قالب المنتجات).
- الموقع والمنشأة: `site-settings` (إعدادات الموقع)، `business-settings` (بيانات الشركة)، `bank-settings` (الحسابات البنكية).

`credentials` و`permissions` يبقيان للمالك فقط **دائمًا**. لا يُنشأ أدمن جديد، ولا تُمنح أي صلاحية افتراضية إضافية. الصلاحيات الحالية فقط هي `analytics`, `datasheet`, `profile`, `contacts`, `leads`.

## لماذا لا يصح تفعيل الأزرار فقط؟

- قيد `admin_users_permissions_check` ودالة `owner_set_admin2_settings` يرفضان مفاتيح الصلاحيات الجديدة.
- وظيفة Supabase `manage-admin-account` ترشح أي مفتاح غير مصرح به من الطلب.
- `admin.js` و`admin-navigation.js` ووحدات الإعدادات فيها قيود Owner-only مستقلة عن القائمة.
- `products` و`sections` لديهما سياسات RLS موجودة بالفعل، لكنهما غير قابلين للتفويض بسبب قيد الصلاحيات؛ أعمالهما تشمل الحذف ويجب اختبارها بعناية.
- جداول `site_settings` و`business_privacy_settings` و`business_public_fields` و`business_bank_accounts` تقيّد الكتابة للمالك. لا يجوز منح جميع الإعدادات لغير المالك مقابل السماح بإعداد واحد.
- مفاتيح `site-settings` و`template-settings` و`search-filters` تكتب إلى **صف مشترك** في `site_settings`. منح كتابة هذا الصف برخصة واحدة سيتيح تغيير إعدادات أقسام أخرى عبر API. الحل المستهدف: **دوال RPC منفصلة تتحقق من الدور والصلاحية وتسمح بالأعمدة المحددة فقط** بدل إطلاق UPDATE شامل.

## قبل دمج الميزة

1. موافقة مالك الموقع **بشكل مستقل** على مراجعة SQL وتطبيقه في مشروع Supabase الفعلي؛ هذه الخطوة ليست موافقة ضمنية.
2. تطوير SQL مرحلي قابل للتراجع، دون حذف البيانات أو منح `credentials` أو `permissions`.
3. اختبار أن الأدمن لا يستطيع تعديل أي جدول أو RPC أو ملف Storage خارج الأجزاء المُفعّلة له، بما في ذلك الطلبات اليدوية المباشرة.
4. تأكيد أن الحساب الحالي يحتفظ بصلاحياته نفسها وأن جميع المفاتيح الجديدة تكون OFF عند الانتقال.
5. تحديث قيود الواجهة والتنقل، وحدات الإعدادات، والـEdge Function، وعدم نشر الواجهة قبل انتهاء اختبارات الأمان.
6. اختبار الدخول والصلاحيات بمعرّفات مُحاكاة أولًا، ثم تطبيق SQL بعد النسخة الاحتياطية وبموافقة المالك.

**هذه الوثيقة والفرع المرتبط لا تنفذان SQL ولا تغيران `admin_users` أو بيانات Supabase.**

## ملف SQL الرسمي للمراجعة (لم يتم تشغيله)

- [فتح SQL المقترح](../supabase/PROPOSED_ADMIN_12_PERMISSIONS_REVIEW_ONLY.sql).
- الخطوة المقترحة لا تمنح الأدمن أي صلاحية جديدة تلقائيًا؛ تقتصر على إضافة مفاتيح التفويض والسياسات المقيدة والدوال المخصصة.
- **مهم:** لا يكفي SQL منفردًا لإكمال الميزة. يلزم بعده تحديث `admin.js` و`admin-navigation.js` ووحدات الفلاتر والموقع والقالب والشركة والبنوك، وكذلك `manage-admin-account` في Supabase Edge Functions، مع اختبارات عزل حقيقية لحساب الأدمن.
- خاصية الحسابات البنكية تحتاج إذن `bank-settings` فقط؛ إعدادات الشركة `business-settings` فقط. لا تُمنح كتابة كاملة لجدول `site_settings` لأحد غير المالك.
- توجد دوال منفصلة: `admin_set_site_toggle` و`admin_save_catalog_filters` و`admin_set_template_field` لتعديل أعمدة محددة. يظل حساب المالك وحده صاحب صلاحية منح الصلاحيات وتغيير بيانات الدخول.
- **حماية الملف الجامع:** جرى تحديث قوائم المراحل القديمة لتحتفظ بالصلاحيات الـ12، وإلحاق الترقية المقترحة حرفيًا بنهاية `SUPABASE_SETUP.sql`. ولأن المراحل التاريخية قد تغيّر إعدادات أخرى، أضفنا حاجز `FL_MASTER_EXISTING_DATABASE_DENIED` الذي يمنع تشغيل الملف الجامع فوق قاعدة موجودة أصلًا. الاختبار المعزول يؤكد المنع قبل تنفيذ أي تعليمات تعديل. بعد الموافقة المنفصلة على التفعيل، يُستخدم ملف الترقية التدريجي فقط.

### مسار التفعيل اللاحق (بعد موافقة منفصلة)

1. تثبيت نسخة الرجوع وفحص النسخة الاحتياطية الموجودة، دون إعادة نسخ أو تعديل بيانات.
2. مراجعة SQL مع اختبار فشل الوصول غير المصرح في قاعدة اختبار معزولة، وليس إنتاج.
3. الموافقة الصريحة على تشغيل هذا SQL في المشروع الحقيقي بعد عرض النسخة النهائية حرفيًا.
4. اختبار صلاحيات الأقسام الـ12 بصلاحيات OFF أولًا، ثم اختبار كل مفتاح وحده وعدم تسرّب الصلاحيات الأخرى.
5. نشر تحديثات الواجهة ووظيفة إدارة الحسابات المتوافقة، وتفعيل أزرار الأقسام الجديدة فقط عندما تنجح الاختبارات.
6. تجربة عملية في حساب الأدمن مع عدم حذف أي منتج أو تعديل بيانات حقيقية أثناء التحقق.

## اختبار PostgreSQL المعزول — دليل التنفيذ

- **تجربة حقيقية للـSQL:** تعمل تلقائيًا في GitHub Actions عبر `.github/workflows/admin-12-postgres.yml` على خدمة PostgreSQL 16 مؤقتة، لا تتصل مطلقًا بمشروع Supabase الفعلي. الملفات `tests/admin-12-db-fixture.sql` و`tests/admin-12-db-rules.sql` تحتوي سجلات ومستخدمين وهميين فقط.
- يُطبّق ملف `supabase/PROPOSED_ADMIN_12_PERMISSIONS_REVIEW_ONLY.sql` كاملًا على قاعدة الاختبار؛ أي خطأ في PostgreSQL يوقف الفحص. ثم تُجرّب طلبات ناجحة وأخرى مرفوضة لهويات Owner وSubadmin وanon، مع اختبار منع الوصول إلى جدول الإعدادات المشترك أو المجلدات الأخرى بالطلب المباشر.
- فحص `sections/products` يختبر صراحة أن حذف قسم يتطلب الصلاحيتين معًا، كما في سياسة `SUPABASE_SETUP.sql`، حتى لو كانت إحداهما وحدها كافية لتحرير بيانات القسم.
- هذه تجربة **محاكاة للهيكل القائم مع سياسات من ملفات المشروع**؛ ليست نسخة من مخطط Supabase الفعلي، ولذلك لا تكشف التغييرات غير الموثقة في سياسات المشروع الحالي أو صلاحيات الدوال الأخرى.
- قبل الموافقة على الإنتاج: مراجعة فعلية **للقراءة فقط** لسياسات `pg_policies` وتعريفات الدوال والأدوار وصلاحيات الملفات في مشروع فلور لايت، دون تعديل بيانات، ثم تطابق المخطط وتحديث اختبارات الحالات السلبية عند الحاجة.
- لا تدمج PR #63، ولا تنشر Edge Function، ولا تشغّل SQL على المشروع الحقيقي، قبل موافقة مستقلة بعد هذه المراجعة.

## فحص دالة تنظيف العملاء والنسخة المنشورة (2026-10-14)

- تمت مراجعة تعريف الدالة الفعلية `public.purge_expired_customer_leads()` في Supabase **بالقراءة فقط**. قبل التحديث المقترح كانت تسمح لأي حساب `subadmin` بتشغيل الصيانة لأنها تستخدم `is_site_admin()` بدل صلاحية `leads`. الدالة ذات `SECURITY DEFINER` وتنفّذ حذف سجلات العملاء المنتهية مدة الاحتفاظ؛ لذلك يجب إغلاق هذا التجاوز قبل تفويض أقسام جديدة.
- التعديل المقترح موجود **داخل معاملة SQL غير المنفذة فقط**: حساب `authenticated` يحتاج `has_admin_permission('leads')` (وتشمل المالك)، بينما تبقى صلاحيات `service_role` ومسار الصيانة الداخلي الموثوق كما كانا، مع رفض `anon` وعدم منح صلاحية تنفيذ عامة.
- يحتفظ نص الدالة بمدة الاحتفاظ الفعلية من `business_privacy_settings` وبالقيمة الاحتياطية 180 يومًا وبحدود 1–36500 يوم وبقيمة عدد السجلات المحذوفة.
- اختبارات PostgreSQL 16 المعزولة تتأكد من رفض طلبات الأدمن بدون `leads` حتى إذا مُنح `search-filters` أو `site-settings` أو `template-settings` أو `business-settings` أو `bank-settings`، ومن نجاح تنظيف سجل اختبار قديم بصلاحية `leads`، وبقاء سجل حديث، ونجاح مسار `service_role` المصرح به، ومن رفض `anon`.
- الفرق الحقيقي في وظيفة Supabase `manage-admin-account` المنشورة (الإصدار 4): قائمة التفويض تحتوي على الخمس القديمة فقط. اقتراح GitHub يضيف الصلاحيات الـ12 عند نشره مستقبلًا. **نطاقات CORS الافتراضية متطابقة** مع المنشور، لكن نسخة GitHub تضيف دعمًا اختياريًا ومقيّدًا لمتغير `ALLOWED_ORIGINS`. يجب مراجعة هذه الميزة وقت نشر Edge Function وعدم إضافة نطاقات غير معروفة.
- مراجعة فعلية للقراءة فقط أكدت أن `purge_expired_customer_leads()` لا تسمح لـ`anon` بالتنفيذ، وتسمح لـ`authenticated` و`service_role`؛ لا يتغيّر ذلك في مسودة الترقية إلا بفرض صلاحية `leads` على الحسابات العادية.
- **تظل الدالة المنشورة في Supabase بصيغتها السابقة** إلى أن يوافق المالك صراحة على تطبيق SQL النهائي. لا ينبغي اعتبار نتيجة CI إصلاحًا منشورًا للمشكلة.



**خطة التنفيذ والتراجع التفصيلية:** [ADMIN_12_PRODUCTION_ROLLOUT_ROLLBACK.md](ADMIN_12_PRODUCTION_ROLLOUT_ROLLBACK.md).

## خطة التفعيل والرجوع — المرجع الآمن

### حماية الإصدار قبل أي موافقة على الإنتاج

1. **احفظ SHA للنسخة المنشورة على main** وSHA للنسخة المرشحة، وتأكد من نجاح النشر والفحوص السابقة. لا تغيّر فرع main قبل اعتماد SQL وخطة نشر Edge Function.
2. **تحقق من النسخة الاحتياطية الموجودة** ومن إمكانية استعادتها؛ لا تعتمد مجرد وجود ملف ZIP أو CSV دون اختبار الاستعادة. لا تنفّذ استعادة على قاعدة الإنتاج للتجربة.
3. **منع تشغيل الماستر التاريخي**: ملف `SUPABASE_SETUP.sql` يُستخدم للتوثيق أو التهيئة الجديدة فقط، ولا يعاد تشغيله على قاعدة إنتاج مهيأة. الترقية الوحيدة المقصودة هي `supabase/PROPOSED_ADMIN_12_PERMISSIONS_REVIEW_ONLY.sql`، بعد موافقة منفصلة وصريحة. يتأكد `tests/admin-12-master-compat.mjs` تلقائيًا من احتفاظ جميع المراحل بالصلاحيات الـ12 وتطابق الملحق النهائي مع الترقية المستقلة، وتتحقق GitHub Actions من رفض تشغيل الملف الجامع على قاعدة موجودة.
4. **موافقة SQL محددة**: اعرض نسخة SQL النهائية بنصها، مع عدد السياسات والدوال المراد تعديلها، واطلب إذنًا منفصلًا لتشغيلها. عدم وجود موافقة يعني عدم التشغيل.
5. **ترتيب التفعيل عند الموافقة لاحقًا**: نفّذ الترقية بعد النسخ الاحتياطي؛ افحص RLS والدوال و`anon/authenticated/service_role`؛ ثم انشر Edge Function بالمصدر المتوافق مع صلاحيات الـ12 مع مراجعة نطاقات CORS؛ ثم ادمج واجهة الإدارة وانشرها. لا تفوّض أي قسم جديد إلا بعد نجاح الخطوات.
6. **الاختبار اليدوي الآمن**: أدمن بصلاحية واحدة يستطيع رؤية هذا القسم فقط ويُرفض تعديل غيره على مستوى قاعدة البيانات؛ إعدادات المالك وإدارة الحسابات تبقى محجوبة. لا تحذف سجلات إنتاج أو ترفع ملف Excel في الاختبار.

### خطة التراجع عند ظهور خلل

- **خلل واجهة فقط**: أعد نشر SHA المستقر السابق على GitHub Pages. راجع كاش PWA ورقم البناء وتأكد من أن الزوار يستلمون الواجهة السابقة. رجوع الواجهة لا يعيد صلاحيات SQL تلقائيًا.
- **خلل وظيفة Edge**: أعد نشر نسخة الوظيفة المحفوظة من قبل التفعيل (بعد التحقق من إعدادات CORS والمتغيرات). لا تفترض أن الرجوع إلى نسخة GitHub القديمة يعيد إصدار Edge المنشور بالضبط.
- **خلل صلاحيات قاعدة البيانات**: لا تحذف السياسات أو تستبدل الدوال عشوائيًا، ولا تعِد تشغيل الماستر التاريخي. قبل التفعيل احتفظ بتعريفات `pg_get_functiondef` و`pg_policies` و`pg_get_constraintdef` وأذونات `EXECUTE` الحالية. جهّز نص تراجع مراجَعًا في معاملة واحدة يعيد التعريفات الملتقطة، ويتأكد أولًا من عدم وجود صلاحيات جديدة مُفعّلة في حساب الأدمن حتى لا يكسر قيد الصلاحيات القديم. ابدأ بتعطيل التغييرات من واجهة المالك فقط إذا كانت متاحة وآمنة. اطلب موافقة منفصلة على تنفيذ التراجع في الإنتاج.
- **الاستعادة الكاملة** ملاذ أخير فقط إذا فشلت خطة التراجع المحددة، ولأنها قد تعيد بيانات المنتجات والعملاء إلى تاريخ سابق وتفقد تغييرات لاحقة. يجب التحقق من نقطة الاستعادة والموافقة على أثر فقد البيانات قبل أي استعادة.

### شروط القبول

- نسخة GitHub والإصدار المنشور موثقان؛ استعادة النسخة الاحتياطية مثبتة في بيئة مستقلة؛ اختبارات PostgreSQL جميعها خضراء.
- SQL النهائي وEdge والواجهة متوافقون؛ لا صلاحيات جديدة تلقائيًا للأدمن؛ وثّق كل اختبار ON/OFF للصلاحيات الـ12.
- **هذه الخطة توثيق فقط** ولا تمنح إذنًا لتنفيذ SQL أو إعادة نشر الموقع أو وظيفة Supabase.
