# خطة التفعيل والرجوع — صلاحيات الأدمن للأقسام الـ12

**الحالة: تجهيز للمراجعة فقط. ليست موافقة على التطبيق في Supabase أو الدمج في GitHub.**

## الملفات المعتمدة للمراجعة

- الملف التاريخي SUPABASE_SETUP.sql مخصص للتثبيت الجديد فقط. يمنع الحاجز FL_MASTER_EXISTING_DATABASE_DENIED إعادة تشغيله فوق أي قاعدة تحتوي على admin_users.
- الملف المنفصل supabase/PROPOSED_ADMIN_12_PERMISSIONS_REVIEW_ONLY.sql هو الترقية المقترحة للمشروع القائم؛ لا يُنفذ دون موافقة جديدة ومنفصلة.
- اختبار tests/admin-12-master-compat.mjs يتحقق من أن جميع مراحل التطبيع التاريخية تحتفظ بالمفاتيح الاثني عشر، وأن الترقية الملحقة بالملف الجامع تطابق نسخة الملف المنفصل حرفيًا.
- اختبار .github/workflows/admin-12-postgres.yml يعمل على خدمة PostgreSQL مؤقتة وبيانات وهمية، ويتحقق أيضًا من رفض إعادة تشغيل الملف التاريخي.

## أ. تثبيت نقطة الرجوع — قراءة فقط

1. حفظ Commit آخر إصدار منشور على main ورابط نشر GitHub Pages الناجح؛ عدم نشر مسودة #63 قبل الاعتماد.
2. التحقق من وجود النسخة الاحتياطية المكتملة سابقًا لـSupabase وصلاحية استعادتها. لا تضع dump أو مفاتيح الدخول في GitHub.
3. أرشفة تعريفات دوال owner_set_admin2_settings وpurge_expired_customer_leads وسياسات RLS وأذونات EXECUTE وقيود admin_users، مع حفظ صلاحيات حساب الأدمن الحالية دون مشاركة بريد الحساب أو هويته في وثائق عامة.
4. أرشفة الكود الفعلي المنشور لوظيفة manage-admin-account، ورقم نسختها وإعداد verify_jwt وقائمة CORS. لا تفترض تطابق نسخة GitHub مع الوظيفة المنشورة؛ فقد ثبت وجود فرق في دعم ALLOWED_ORIGINS.

## ب. الموافقة قبل التنفيذ

يجب طلب موافقة صريحة ومنفصلة من مالك الموقع تحدد مشروع Supabase ونسخة SQL النهائية وCommit الهدف. تأكيد «أكمل» أثناء المراجعة والاختبارات لا يمنح إذنًا بتغيير الإنتاج.

## ج. التفعيل بالتسلسل — بعد الموافقة فقط

1. تثبيت نقطة الرجوع والتأكد من سلامة النسخ الاحتياطية وعدم وجود تغيير موازٍ.
2. تنفيذ **ملف الترقية المنفصل فقط** ضمن المعاملة المحددة؛ عدم تشغيل SUPABASE_SETUP.sql على قاعدة الإنتاج.
3. التحقق من وجود الدوال الجديدة والسياسات المطلوبة، ومن أن قائمة الأدمن الحالية لم تتغير وأن الصلاحيات السبع الجديدة لم تُمنح تلقائيًا.
4. مراجعة سماح التنفيذ لـauthenticated وservice_role ومنع anon، وأن purge_expired_customer_leads يشترط leads للحسابات العادية.
5. نشر وظيفة manage-admin-account المتوافقة بعد التحقق من CORS وverify_jwt، ثم اختبار تسجيل دخول المدير والأدمن بصلاحياتهما القديمة.
6. دمج واجهة PR #63 ونشر GitHub Pages والتحقق من Actions والموقع المنشور والكاش وPWA.
7. اختبار كل ON/OFF على حدة من حساب المدير، ثم قراءة قائمة الأدمن بحساب محدود؛ يجب ألا تظهر بيانات الدخول ولا إدارة الصلاحيات للأدمن.
8. لا تنفذ تجارب حذف منتجات أو سجلات عملاء أو تغيير حساب بنكي حقيقي عند فحص الصلاحيات. اختبارات الكتابة/الحذف تُنفذ في البيئة المعزولة أو ببيانات وهمية مصرح بها صراحة.

## د. مؤشرات إيقاف التفعيل

- خطأ SQL أو تعارض مع السياسات الفعلية أو فقدان صلاحية مالك.
- تغير مفاتيح/حسابات الأدمن بلا قرار منه.
- قدرة أدمن على تعديل قسم غير مفعل له أو تشغيل تنظيف العملاء دون leads.
- فشل التصدير أو تسجيل الدخول أو نشر GitHub Pages.

توقف عن التفعيل عند أي فشل. لا تعاود تشغيل الملف الجامع، ولا تستخدم استعادة كاملة عشوائية.

## هـ. الرجوع الآمن — إجراءات الإنتاج تحتاج إذنًا منفصلًا

1. **الموقع:** العودة إلى آخر Commit ونشر ناجحين موثقين، دون المساس ببيانات Supabase ما لم يكن سبب العطل فيها.
2. **وظيفة Edge:** إعادة نشر المصدر السابق الذي تم حفظه فعليًا مع verify_jwt وقائمة CORS، وليس نسخة GitHub مفترضة.
3. **قاعدة البيانات:** راجع مفاتيح الأدمن التي أضيفت منذ التفعيل؛ إلغاؤها تغيير صلاحيات ويحتاج موافقة. خذ نسخة من الحالة قبل تقليص قيد القائمة إلى خمسة.
4. إزالة السياسات والدوال الجديدة المحددة فقط عند الحاجة، وإرجاع تعريف owner_set_admin2_settings والقيود من تعريفات الإنتاج السابقة المحفوظة؛ لا تحذف المنتجات أو الجداول أو بيانات المنشأة.
5. **الاحتفاظ بإصلاح قيد leads في purge_expired_customer_leads** حتى عند الرجوع عن بقية التوسعة، لأنه يعالج تجاوز صلاحيات حقيقيًا. إذا تعطلت الصيانة الآلية، افحص هوية مستدعيها بدل إتاحة الحذف لكل أدمن.
6. الاستعادة من نسخة احتياطية كاملة هي خيار أخير فقط بعد فهم الضرر والحصول على موافقة مستقلة.

## و. معايير القبول النهائية

- جميع الجداول RLS ما زالت مفعلة وأذونات الجمهور محمية.
- الوصول عبر API لا يتجاوز صلاحيات ON/OFF.
- تسجيل المدير والأدمن والكتالوج والصور وPDF وExcel وPWA يعمل دون أخطاء.
- توثيق موافقة المالك النهائية في سجل الفحص.

**هذه الوثيقة لا تنفذ أي SQL، ولا تسمح بدمج PR #63 تلقائيًا.**
