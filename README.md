# بصائر الخليج — Flower Light v117

موقع GitHub Pages ثابت لإدارة وعرض منتجات Flower Light، مع Supabase للمصادقة والبيانات والتخزين وEdge Functions.

**الإصدار الحالي:** v117 (`package.json` = `1.1.7`).


## ما الجديد في v117 — إكمال تعريب/ترجمة البطاقة الرئيسية

- أصلح نصوص البطاقة التي كانت تعود للعربية بعد تحميل البيانات من Supabase: المسمى الوظيفي، واسم الشركة، وملخص المنتجات ومقدمة الكتالوج، ووسائل التواصل، وتذييل البطاقة.
- حالة الإنجليزية تعرض المسمى الوظيفي الإنجليزي المخزن بالفعل، وتستخدم الاسم الإنجليزي للعلامة والشركة والفروع من قاعدة البيانات متى أدخله المدير.
- أضيفت في لوحة المدير حقول اسم العلامة واسم الشركة بالإنجليزية، وتسمية كل وسيلة/فرع بالإنجليزية. أسماء الأشخاص والبيانات المالية الرسمية لا تُترجم آليًا.
- الحسابات البنكية تعرض عدادًا وحقولًا وأزرار نسخ حسب لغة الزائر. بيانات المنشأة تُترجم تسميات الحقول وتبقي القيم الرسمية دون تعديل.
- تتحدث البيانات المعروضة فور تبديل اللغة دون إعادة تحميل الصفحة، وتعود العربية الأصلية عند الرجوع.
- **لتفعيل حفظ حقول البطاقة الجديدة** طبّق `supabase/UPGRADE_EXISTING_V117.sql` باستخدام SQL Editor. الرسالة المتوقعة `PUBLIC_CARD_I18N_V117_OK`. وإذا لم تُطبّق ترقية المنتجات v116، شغّل `supabase/UPGRADE_EXISTING_V116.sql` أيضًا. لا تشغّل الملف الكامل `SUPABASE_SETUP.sql` على قاعدة حية.
- الأسعار والصور وأكواد المنتجات وسياسات RLS لم تُعدّل.

## ما الجديد في v116 — حقول اللغتين للأقسام والمنتجات

- لوحة المدير: اسم القسم ووصفه بالعربية والإنجليزية، واسم المنتج ووصفه باللغتين، واسم وقيمة كل مواصفة بالإنجليزية إلى جانب حقول العربية.
- شاشة الزوار: تستخدم الترجمة المحفوظة عند اختيار English وتعود إلى القيم العربية الأصلية عند اختيار العربية؛ يتغير عنوان القسم وأزرار المشاركة/التحميل، ويبقى البحث متاحًا بالاسم في اللغتين.
- لا توجد ترجمة افتراضية تخمينية للمحتوى التجاري؛ إذا لم تُملأ خانة English فستظهر القيمة العربية الحالية دون حذفها.
- **مهم: قبل استعمال حفظ الأقسام أو المنتجات الجديدة، شغّل SQL الآمن `supabase/UPGRADE_EXISTING_V116.sql` مرة واحدة على مشروع Supabase الإنتاجي.** يعيد `BILINGUAL_CATALOG_V116_OK` إذا نجح. لا تشغّل `SUPABASE_SETUP.sql` على القاعدة الحية.
- الإضافة لا تمس الأسعار أو المخزون أو الصور أو الهويات أو صلاحيات RLS؛ تظل ملفات التصدير بالنمط الحالي.
- الاختبارات: التبديل بين اللغتين، الترجمة المعتمدة، الفلاتر، واجهة الإدارة، ونسخة المتصفح.

## ما الجديد في v111M — قسم مستقل لفلاتر البحث

- نُقلت إدارة الفلاتر من **إعدادات الموقع** إلى قسم مستقل باسم **فلاتر البحث** داخل لوحة المدير.
- يستطيع المالك اختيار أي فلتر قياسي يريد إظهاره للزوار أو إخفاء جميع الفلاتر والإبقاء على البحث النصي فقط.
- يمكن للمالك إنشاء **فلتر خاص** جديد مثل «نوع العدسة» أو «طريقة التركيب». بعد حفظه يظهر أيضًا ضمن قائمة **نوع المواصفة** عند إضافة/تعديل المنتج.
- الفلاتر الخاصة تستخدم مفتاحًا ثابتًا مشتركًا بين المنتجات، لذلك يمكن استخدامها بأمان كفلتر عام.
- أصبحت خيارات الفلاتر **مترابطة**: عند اختيار قيمة في فلتر، تتحدث قيم بقية الفلاتر لتعرض الخيارات المتوافقة مع الاختيارات الحالية والبحث النصي.
- قيم الفلاتر ما زالت تُستخرج تلقائيًا من المنتجات، فلا تظهر خيارات غير موجودة في البيانات.
- قاعدة البيانات تحتاج تشغيل `supabase/UPGRADE_EXISTING_V111.sql` مرة واحدة لإضافة `catalog_custom_filters`.

## ما الجديد في v111E — ترتيب أزرار المنتج

- عند تفعيل قائمة طلب عرض السعر تصبح أزرار بطاقة المنتج شبكة متناسقة 2×2: **تحميل + مشاركة** في الصف الأول، و**واتساب + طلب عرض السعر** في الصف الثاني.
- زر واتساب وزر طلب عرض السعر لهما عرض وارتفاع متقاربان في الصف الثاني.
- عند إخفاء طلب عرض السعر من لوحة المدير يعود التخطيط تلقائيًا إلى الشكل السابق: **تحميل + مشاركة** في الأعلى و**واتساب بعرض كامل** في الأسفل.
- لا توجد أي migration أو تغيير قاعدة بيانات إضافي في v111E.


## ما الجديد في v111D — تحكم المدير بظهور طلب عرض السعر

- أضيف إعداد للمالك داخل لوحة المدير باسم **إظهار قائمة طلب عرض السعر للزوار**.
- عند إيقافه تختفي أزرار «أضف لقائمة الطلب» والشريط العائم ونافذة الطلب من الموقع العام، ولا يمكن الإضافة أو الإرسال عبر واجهة القائمة.
- عند إعادة تشغيله تعود الميزة، وتبقى القوائم المحلية المحفوظة على أجهزة الزوار محفوظة.
- الإعداد مخزن في `site_settings.quote_list_enabled` وقيمته الافتراضية `true` حفاظًا على سلوك v111C.
- أضيفت migration مستقلة وملف `supabase/UPGRADE_EXISTING_V111.sql` للترقية الآمنة من النسخة الحالية.


## ما الجديد في v111C — المهمة 4: قائمة طلب عرض السعر

- يمكن للزائر إضافة عدة منتجات إلى قائمة واحدة وتحديد كمية كل منتج.
- القائمة تحفظ محليًا في المتصفح بالمفتاح `fl_quote_list_v1` ولا تنشئ سجلات جديدة في قاعدة البيانات.
- الحد الأقصى 30 صنفًا، والكمية لكل صنف من 1 إلى 9999.
- يظهر شريط عائم «قائمة الطلب (N)» عند وجود أصناف، وتفتح نافذة يمكن منها تعديل الكميات والحذف وإضافة اسم وملاحظات اختيارية.
- الإرسال يجمع الأصناف في رسالة واتساب واحدة مرتبة، ويمنع الإرسال إذا تجاوز الرابط الحد الآمن التقريبي 1800 حرف.
- أحداث التحليلات الخاصة بالقائمة ترسل عدد الأصناف فقط دون الاسم أو الملاحظات أو أي بيانات شخصية.
- جدول `quote_requests` التاريخي لم يُحذف لأن عدد صفوفه في قاعدة الإنتاج لم يُتحقق منه ضمن هذه المهمة؛ لا توجد migration مدمرة في v111C.


## ما الجديد في v111B — المهمة 3: صفحات SEO ومشاركة ثابتة

- البناء يولّد صفحة HTML ثابتة لكل منتج ظاهر في `dist/p/<id>/index.html` ولكل قسم ظاهر في `dist/c/<slug>/index.html`.
- الصفحات الثابتة تحتوي `title` و`description` و`canonical` وOpen Graph وTwitter Card، وللمنتج JSON-LD من نوع `Product`.
- صورة المشاركة للمنتج تؤخذ من صورة المنتج العامة في bucket `product-images`، مع fallback إلى `share-image.jpg` إذا لم توجد صورة صالحة.
- يتم توليد `dist/sitemap.xml` تلقائيًا من المنتجات والأقسام الظاهرة فقط، مع `lastmod` من `updated_at` متى توفر.
- روابط المشاركة من الواجهة أصبحت `/p/<id>/` و`/c/<slug>/` بدل روابط query، بينما يبقى `?product=` و`?category=` مدعومًا للروابط القديمة ولتحويل الزائر من الصفحة الثابتة إلى الكتالوج التفاعلي.
- Service Worker لا يعترض مسارات `/p/` و`/c/` حتى لا يقدم نسخة HTML قديمة.
- GitHub Pages يعيد البناء تلقائيًا كل 6 ساعات، إضافة إلى push و`workflow_dispatch`.
- إذا تعذر جلب بيانات Supabase أثناء بناء الإنتاج يفشل build بوضوح بدل نشر موقع يحذف صفحات المشاركة. للاختبار المحلي فقط يمكن استخدام `FL_SKIP_STATIC_PAGES=1`.
- أضيف `tests/static-pages.mjs` للتحقق من canonical وOG والصور والهروب من HTML واستبعاد المنتجات المخفية والسitemap وفشل الجلب.
- لا توجد تغييرات قاعدة بيانات في v111B.

## النشر على GitHub Pages

استخدم **GitHub Actions فقط**:

`Settings → Pages → Build and deployment → Source → GitHub Actions`

Source = GitHub Actions

لا تستخدم **Deploy from a branch**، ولا ترفع `dist` أو `node_modules` يدويًا. Workflow `pages.yml` يقوم بـ:

1. `npm ci`
2. `npm run test:static`
3. `npm run build`
4. تثبيت Chromium
5. `npm run test:browser` على `dist`
6. نشر `dist` إلى GitHub Pages

`npm run build` يحتاج اتصالًا بالإنترنت وقت البناء فقط لتحضير نسخة Supabase المثبتة إلى `dist/supabase-vendor.js`. ملف المصدر `index.html` يبقي رابط CDN المثبت لتسهيل المعاينة المباشرة غير المبنية، لكن build يستبدله بملف محلي ويزيل jsDelivr من CSP الإنتاجي؛ لذلك الزيارة المنشورة لا تعتمد على CDN لـSupabase وقت التشغيل.
